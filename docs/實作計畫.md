# 實作計畫：智慧訂單與促銷引擎

2026-10-30

本文件是**完成後整理**的，記錄實際的設計與順序，不是動工前寫的計畫。實作過程使用 AI 工具（Claude Code）。

設計目標是讓新增折扣或通知通道時不用改既有類別，並讓付款不被通知卡住。

## 架構

```
                         OrderService
                  (createOrder、pay、ship)
                 /            |            \
           算折扣            存取           非同步發送
               /              |              \
    PromotionEngine   InMemoryOrderRepository   NotificationDispatcher
    依序套用折扣       ConcurrentHashMap         每通道一條 virtual thread
           |                  |                       |
    DiscountStrategy        Order              NotificationChannel
    - Threshold...          - OrderItem        - MockEmailChannel（預設）
    - Holiday...            - OrderStatus      - SmtpEmailChannel（smtp 模式）
    - MemberLevel...        - MemberLevel      - MockSlackChannel
```

新增折扣或通道，只要在最下排多一個實作，上兩層不用改。付款只改狀態並交給背景發送，不等通知完成。

## 需求對照

| 模組 | 需求 | 實作方式 | 類別 |
| --- | --- | --- | --- |
| 一 | 項目小計、金額精確 | `BigDecimal` 計算，建立時驗證欄位 | `OrderItem` |
| 一 | 訂單總價、狀態 | Stream 加總；狀態只能 PENDING → PAID → SHIPPED | `Order`、`OrderStatus` |
| 二 | 滿額折 | 滿 $1,000 折 $100，滿 $2,000 折 $250 | `ThresholdDiscountStrategy` |
| 二 | 節慶折 | 11/11、12/25 打 9 折 | `HolidayDiscountStrategy` |
| 二 | 會員折 | BRONZE 無折扣、SILVER 95 折、GOLD 9 折 | `MemberLevelDiscountStrategy` |
| 二 | 系統擴展性 | Strategy 模式，由引擎依序執行 | `DiscountStrategy`、`PromotionEngine` |
| 三 | PAID 後同時發通知 | 每個通道一條 virtual thread | `NotificationDispatcher` |
| 三 | Email 與 Slack | 同一介面的多個實作 | `NotificationChannel`、`MockEmailChannel`、`SmtpEmailChannel`、`MockSlackChannel` |
| 範圍限制 | 不連資料庫 | `ConcurrentHashMap` | `InMemoryOrderRepository` |

## 需求不明確時的決策

| 問題 | 決策 | 理由 |
| --- | --- | --- |
| Email 要 Mock 還是實際寄送（題目互相矛盾） | 兩者都做，預設 Mock，設定 `app.notification.email.mode=smtp` 切換 | 不管題意是哪個都能滿足 |
| 三種折扣能否併用 | 全部併用，依序為滿額 → 節慶 → 會員 | 題目稱為多重折扣；順序可改 `@Order` |
| 滿額折兩級是否累加 | 不累加，只取最高一級，剛好滿額也算 | 滿額折的常見定義 |
| `discountedAmount` 的意思 | 折扣後應付金額 | 通知與付款直接使用這個金額 |
| 四捨五入 | 全部算完才四捨五入到小數 2 位 | 避免中途捨入累積誤差 |
| Java 版本 | 17 改為 21 | virtual threads 在 21 才是正式功能，仍符合 Java 17+ |

折扣併用與順序是自行決定的，尚待面試官確認。

## 實際實作順序

1. 確認環境（JDK 21、Maven）與既有的 Spring Boot 空專案。
2. 寫模型層、折扣策略、通知、服務層與對應測試。
3. 更新 `pom.xml`：Java 21、郵件套件、GreenMail 測試套件。
4. 跑全部測試，再補 `smtp` 模式的端到端測試。
5. 加上手動測試入口 `ManualDemo`，驗證 Mock 模式與 Email 失敗情境。
6. 做變異驗證，確認測試能抓到錯誤。

測試結果與未驗證項目見 [測試報告](測試報告.md)。
